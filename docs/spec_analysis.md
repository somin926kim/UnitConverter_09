## 1. 요약

현재 코드는 **프로토타입 수준의 단일 함수 스크립트**이며, README에 명시된 품질 요구사항(OCP, SRP, 입력 검증)과 추가 요구사항(설정 외부화, 동적 단위 등록, 출력 포맷)을 **전혀 충족하지 않는다**.  
단위 3개(meter, feet, yard)에 대한 최소 변환만 동작하며, 테스트 코드·설정 파일·클래스 구조가 존재하지 않는다.

| 구분 | 현재 상태 | PRD 목표 |
|------|-----------|----------|
| 아키텍처 | 단일 `main()` 함수 | OCP/SRP를 만족하는 클래스 구성 |
| 단위 확장 | 코드 수정 필수 | 기존 코드 변경 최소화 |
| 입력 검증 | 부분 구현 | 음수·형식·없는 단위 전부 검증 |
| 설정 | 하드코딩 | JSON/YAML 외부 설정 |
| 테스트 | 없음 | 단위 변환·검증 TC 필수 |

## 2. 레거시 코드 스멜

### 2.1 OCP (Open-Closed Principle) 위반

| # | 스멜 | 위치 | 설명 |
|---|------|------|------|
| OCP-1 | **단위별 if/elif 분기** | `UnitConverter.py:16-24` | 새 단위 추가 시 `main()` 내부 분기를 직접 수정해야 한다. 확장에는 **닫혀 있고**, 변경에는 **열려** 있어야 하는 OCP와 정반대이다. |
| OCP-2 | **출력 대상 하드코딩** | `UnitConverter.py:27-32` | 변환 결과를 meter/feet/yard 3줄로 고정 출력한다. 단위가 N개가 되면 N줄의 `print`를 추가해야 한다. |
| OCP-3 | **변환 비율 매직 넘버** | `UnitConverter.py:19-21, 27-28` | `3.28084`, `1.09361`이 코드에 직접 박혀 있다. 비율 변경·단위 추가 시 **항상 소스 수정**이 필요하다. |
| OCP-4 | **출력 포맷 고정** | `UnitConverter.py:30-32` | f-string 텍스트 출력만 지원한다. JSON/CSV/표 형태 추가 시 `main()`을 수정해야 한다. |
| OCP-5 | **추상화·인터페이스 부재** | 전체 | `UnitConverter`, `UnitRegistry`, `OutputFormatter` 등 확장 지점이 없다. README가 요구하는 "OCP를 만족하는 인터페이스"가 전혀 없다. |

**OCP 위반 핵심:** 단위·비율·출력 형식 중 **하나라도 바뀌면 `main()`을 열어서 수정**해야 한다.

### 2.2 SRP (Single Responsibility Principle) 위반

| # | 스멜 | 위치 | 설명 |
|---|------|------|------|
| SRP-1 | **God Function** | `main()` 전체 | 하나의 함수가 ① 사용자 입력 ② 파싱 ③ 검증 ④ 단위→기준단위 변환 ⑤ 기준단위→전 단위 변환 ⑥ 포맷팅 ⑦ 출력을 모두 담당한다. |
| SRP-2 | **클래스 구조 부재** | 전체 | README는 "SRP를 만족하는 **클래스 구성**"을 요구하나, 클래스·모듈 분리가 전혀 없다. |
| SRP-3 | **I/O와 도메인 로직 결합** | `UnitConverter.py:2, 30-32` | `input()`/`print()`가 변환 로직과 같은 함수에 있어, 테스트·재사용·CLI/API 분리가 불가능하다. |
| SRP-4 | **파싱과 검증 혼재** | `UnitConverter.py:4-14` | 형식 검사(`:` 존재), 토큰 분리, 숫자 변환, 예외 처리가 한 블록에 섞여 있다. |
| SRP-5 | **변환 정책과 표현 정책 결합** | `UnitConverter.py:26-32` | meter 기준 변환 계산과 출력 문자열 생성이 분리되지 않았다. |

**SRP 위반 핵심:** 책임 경계가 없어 **한 가지 변경(예: 출력 포맷)이 전체 함수 수정**으로 이어진다.

### 2.3 입력 검증 부족

README 품질 요구: *"입력 값 검증 (음수, 잘못된 형식, 없는 단위)"*

| # | 검증 항목 | PRD 요구 | 현재 구현 | Gap |
|---|-----------|----------|-----------|-----|
| VAL-1 | **음수 값** | 필수 | 미검증 — `-1` 입력 시 그대로 변환·출력 | ❌ 미구현 |
| VAL-2 | **잘못된 형식 (`:` 없음)** | 필수 | ✅ `':' not in input_str` 검사 | 구현됨 |
| VAL-3 | **잘못된 숫자** | 암시적 | ✅ `float()` + `ValueError` 처리 | 구현됨 |
| VAL-4 | **없는 단위** | 필수 | ✅ `Unknown unit` 메시지 | 구현됨 |
| VAL-5 | **빈 입력** | 암시적 | 미검증 — Enter만 누르면 `Invalid format` (간접 처리) | ⚠️ 불명확 |
| VAL-6 | **빈 단위/값** | 암시적 | 미검증 — `:2.5`, `meter:` 허용 가능 | ❌ 미구현 |
| VAL-7 | **공백 처리** | 암시적 | 미검증 — ` meter:2.5 ` → unknown unit | ❌ 미구현 |
| VAL-8 | **콜론 주변 공백** | 암시적 | 미검증 — `meter : 2.5` → unknown unit | ❌ 미구현 |
| VAL-9 | **0 값** | 암시적 | 허용 (비즈니스상 문제 없을 수 있음) | — |
| VAL-10 | **특수 float (`inf`, `nan`)** | 암시적 | 미검증 — `float('inf')` 통과 | ❌ 미구현 |
| VAL-11 | **대소문자 단위명** | 암시적 | 미정의 — `Meter`는 unknown | ⚠️ 정책 미정 |

**검증 부족 핵심:** PRD에서 **명시적으로 요구한 음수 검증이 빠져 있고**, 실사용에서 흔한 **공백·빈 토큰** 케이스도 처리하지 않는다.

### 2.4 확장성 문제

| # | 문제 | 설명 | 영향 |
|---|------|------|------|
| EXT-1 | **선형적 코드 증가** | 단위 N개 → 입력 분기 N개 + 출력 N줄. O(N) 코드 중복. | 단위 추가마다 회귀 위험 증가 |
| EXT-2 | **기준 단위(meter) 고정** | 모든 변환이 meter 경유로 하드코딩. 기준 단위 변경 시 전면 수정. | 다중 카테고리(무게, 온도) 확장 불가 |
| EXT-3 | **비율 이중 정의** | meter→feet(`* 3.28084`)와 feet→meter(`/ 3.28084`)가 별도 상수로 존재. | DRY 위반, 불일치 버그 가능 |
| EXT-4 | **설정 외부화 없음** | 비율·단위 목록이 코드에만 존재. | 배포 없이 비율 조정 불가 |
| EXT-5 | **동적 단위 등록 없음** | 런타임에 `1 cubit = 0.4572 meter` 등록 불가. | PRD 추가 요구사항 전면 미충족 |
| EXT-6 | **출력 포맷 확장 불가** | JSON/CSV/표 선택 기능 없음. | API·배치 연동 불가 |
| EXT-7 | **테스트 불가 구조** | `input()`/`print()` 직접 호출, 순수 함수·DI 없음. | 자동화 TC 작성 곤란 |
| EXT-8 | **패키지/모듈 구조 없음** | 단일 `.py` 파일. | 협업·CI·배포 확장 어려움 |
| EXT-9 | **출력 정밀도 미정의** | PRD 예시는 `8.2 feet`(소수 1자리)이나 코드는 전체 float 출력. | UX·테스트 기준 불일치 |

## 5. 권장 리팩토링 방향 (참고)

README Activities 순서와 PRD Gap을 기준으로 한 **목표 구조**이다. (구현 지침이 아닌 분석 부록)

```
UnitConverter.py          # CLI 진입점 (얇은 main)
├── domain/
│   ├── unit.py           # Unit, ConversionRate
│   └── converter.py      # UnitConverter (변환만)
├── infrastructure/
│   └── config_loader.py  # JSON/YAML 로드
├── application/
│   ├── parser.py         # 입력 파싱·검증
│   ├── registry.py       # 동적 단위 등록
│   └── formatter.py      # JSON/CSV/Table 출력 (Strategy)
├── config/
│   └── units.json        # 변환 비율
└── tests/
    ├── test_converter.py
    ├── test_validation.py
    └── test_formatter.py
```

**우선순위 제안:**

1. **SRP 분리** — 파싱 / 변환 / 출력을 클래스·모듈로 분리 (테스트 가능하게)
2. **OCP 적용** — `UnitRegistry` + `OutputFormatter` 인터페이스로 확장 지점 확보
3. **입력 검증 보강** — 음수, strip, 빈 토큰, `inf`/`nan` 거부
4. **설정 외부화** — `units.json` 로드
5. **동적 등록 & 출력 포맷** — 추가 요구사항
6. **TC 작성** — 변환 정확도 + 검증 케이스

## 6. 결론

`UnitConverter.py`는 **동작하는 최소 프로토타입**이지만, README PRD가 정의한 **아키텍처 품질·확장성·테스트·추가 기능**과는 큰 간극이 있다.  
가장 시급한 Gap은 **OCP/SRP를 위한 구조 분리**, **음수 포함 입력 검증 완성**, **테스트 코드 부재**이며, 이후 **설정 외부화 → 동적 등록 → 출력 포맷** 순으로 추가 요구사항을 구현하는 것이 PRD Activities 흐름과 일치한다.
